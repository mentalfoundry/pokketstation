# PocketStation application notes

Facts here are about **writing PocketStation applications** — the container format, how the real BIOS discovers and launches an app, and how the app-selection screen renders an app's title/icon — as opposed to [hardware-notes.md](hardware-notes.md), which documents this emulator's own CPU/peripheral implementation. This file is meant to grow into reference material for a future PocketStation dev kit.

Same trust order as hardware-notes.md: (1) direct testing against real hardware, (2) tracing real BIOS/app execution with `tools/inspect.c` against real dumps (never committed - see `testdata/`, gitignored), (3) official register documentation. Facts confirmed against the real `110`-revision retail BIOS (`J110.bin`/`C110`) are called out as such where the BIOS revision matters.

**[`pk_timing_bench/`](../pk_timing_bench/)** (top-level directory) is a real, working example of everything in this file put into practice - a homebrew memory-timing benchmark app, its full build source, and a real-hardware-findings writeup. Several facts below (VRAM/FLASH access width, Timer0 wraparound) were discovered building and debugging it on real retail hardware.

## App file format: PSX Title Sector

PocketStation apps are **not** GME (that's the DexDrive whole-card dump format, `.gme` — needs its container header stripped down to the raw 128KB before it'll load here). The real container is the **PSX Title Sector**, an 80-byte header followed by icon data, an optional snapshot, a function table, and the executable body:

- Offset `0x00–0x4F`: standard PS1 memory-card title/icon header fields.
- Offset `0x50–0x5F`: PocketStation-specific — icon frame counts, an `"MCX0"`/`"MCX1"` identifier at `0x52`, entry point + THUMB-mode flag (bit 0) at `0x5C`.
- If the identifier is `MCX1`: an `0x800`-byte snapshot follows (saved ARM register/RAM state), then the function table and executable body. `MCX0` skips the snapshot.

A PocketStation app extracted as a single PS1 save (most PS1 save-management tools export these as `.mcs`) is this same Title Sector body, just prefixed with one real PS1 directory frame (`0x80` bytes: in-use marker, little-endian data size at `0x04`, link/filename fields). `psemu_load_mcs` strips that frame and validates the size against it, then defers to the same Title Sector loading `psemu_load_app` does - both frontends try `.pss` first and fall back to `.mcs` regardless of the file's actual extension.

**PocketStation apps are frequently bundled as multi-block linked memory-card files** together with the game's regular PS1 save, not as a standalone single 8KB block. A naive per-block scan for the `MCX0`/`MCX1` magic will find the right *first* block but silently miss the rest of the app if you don't follow the card's actual directory (block 0): each of the 15 data-block frames is 128 bytes with allocation state at offset `0x00` (`0x51`=first/solo, `0x52`=middle, `0x53`=last, `0xA0`=free), total filesize at `0x04`, and a next-block link at `0x08` (a little-endian u16, 0-based among the 15 data blocks - add 1 to get the physical block number, `0xFFFF` sentinel = end of chain).

## App-selection and dispatch

Reverse-engineered directly from real BIOS disassembly:

1. A helper returns a selected app-slot index from RAM: `*(u16*)0x000000D0` if nonzero, else `*(u8*)0x000000CE`.
2. **`FLASH2` carries the exact same directory structure as a PS1 memory card** - the kernel reads the directory frame at `FLASH2 + slot*128` and walks the chain via the frame's next-block link, accumulating a bitmask of every physical block belonging to that app.
3. Writes that bitmask to `F_BANK_FLG` and commits (`2` to `FLASH_CTRL+0`).
4. Reads the entry point from `FLASH2 + slot*8192 + 0x5C` (the resolved physical block).
5. Validates the block's header a second time via two Thumb helper functions (reached through classic ARM↔Thumb `add lr,pc,#1 / bx lr` interworking trampolines) before deciding whether to jump fresh or resume from an `MCX1` snapshot.
6. Clears user RAM (`0x200-0x7FF`), switches to User mode, sets User SP to `0x800`, and `BX`es to the entry point.

**A single loaded app (`.pss`/`.mcs`) needs a synthesized directory to be reachable this way** - `flash_load_app` builds one: a card header, one directory frame per app block chained starting at slot 1, and the app's own data starting at physical block 1. **Directory frame offset `0x10` (byte 6 of the filename field) must be ASCII `'P'`**, or the BIOS's menu-browsing code (separate from, and running before, the dispatch routine above) won't let a user navigate to/select the slot at all - every other filename byte can be garbage. This mirrors a real PS1 convention: a save bundling a PocketStation app has its product-code's mandatory hyphen (e.g. `SLUS-00892`) replaced with `P`. See `core/src/flash.c`'s `test_flash_load_app_synthesizes_directory` (in `tests/cpu_test.c`).

**The real, hardware-confirmed button sequence to reach a single loaded app from a cold boot** (see `docs/hardware-notes.md`'s CPU-adjacent boot notes and `tools/inspect.c`'s `button_sim==3`): after the HELLO/heart/beep power-on animation, press **Down** once then **Action** to get past the date/time screen, then **Right** once to move from the clock screen to the app (**Action** launches it from there). Real taps are brief (~40ms); a deliberate, clean press-and-release reads more reliably than mashing - the real BIOS's own input handling sometimes needs more than one clean attempt to register a given press, not because the sequence is wrong.

## Browse-screen icon/graphic

**This entire section was reverse-engineered by directly tracing a real BIOS's execution against a real app and validated by user testing - not by decoding header fields and guessing at a format.** Ground truth only comes from single-stepping the real BIOS and watching which memory it actually touched.

**The real icon lives immediately after the standard PS1 save icon's own frame data** (i.e. `FLASH1_BASE + 0x80 + std_frames*128` once the app is banked in, `std_frames` being the 1/2/3 encoded by the standard PS1 icon-flag byte at Title Sector `0x02`) - not `0x60`, despite `0x60` being where the icon data would start under a standard PS1-save-icon reading of the format. A prior version of this emulator's own homebrew test app placed its own code right after the standard icon, which silently got read back *as* icon data (its first instruction's raw encoding showed up verbatim where a real palette/pixel value should be) - hence "icon renders as garbage/blank" the first several times this was attempted. For a single-frame indirect-layout app specifically (a 1-frame standard icon) this location is body offset `0x100`, which is where the description below was originally anchored - but it isn't a fixed offset in general, see below.

Layout, confirmed via live tracing (BIOS addresses below are for the `110`-revision retail BIOS, `J110.bin`) and cross-checked against three further real apps (a single-frame icon, a slow 2-frame-toggle icon, and a fast 3-frame animated icon - see `testdata/`, gitignored):

- **Two distinct layouts exist**, and which one an app uses isn't yet tied to a confirmed selector bit - it's inferred from the PocketStation-specific header byte at Title Sector `0x50`, which is `0` for both indirect-layout apps seen so far and matches the frame count for the one inline-layout app seen so far. Treat that correlation as a hypothesis (static cross-file analysis, not BIOS-traced), not a confirmed selector.
  - **Indirect (2 of the 3 apps checked here):** an 8-byte header sits right after the standard icon - `word @ +0x00` is a flags/count word, `word @ +0x04` is an absolute FLASH1 pointer to the actual bitmap data, which can sit anywhere in FLASH1 (one real app points at a location near the very end of its own body, nowhere near the icon header - confirming the BIOS's pointer recovery, `(pointer - FLASH1_BASE) / 4`, really is meant to be computed/relocatable, not just theoretically so).
  - **Inline (one app checked here, a 3-frame animated icon):** no header, no pointer - the bitmap frames sit directly, contiguously, right where the standard icon's data ends.
- **The flags word's bit meaning is now partly decoded, from comparing a 1-frame, a 2-frame, and a third 1-frame example:** low 16 bits = on-device icon frame count (`1` for a static icon, `2` for the slow-toggling one). High 16 bits correlate with animation speed (the 1-frame app's static icon: `1`; the slow ~1-2s-toggle icon: `0x30`) - plausibly a per-frame delay, larger = slower, but this is circumstantial (3 data points, no BIOS/timer trace confirming the unit), not confirmed.
- **At the bitmap location: one 128-byte 32×32 1bpp bitmap per frame (frame count per the flags word for the indirect layout, or per the standard icon's own frame count for the inline layout), stored back-to-back** - byte-for-byte the *same packing LCD VRAM itself uses* (32 rows × 4 bytes, bit 0 = leftmost pixel of each byte's 8-pixel span, 1 = black/lit). No palette, no 4-bit indexing, despite the byte count (128) coincidentally also matching a standard PS1 4bpp 16×16 icon bitmap - that similarity is what made the wrong model plausible-looking for as long as it did.
- **For a single-frame indirect-layout icon specifically**, the 128 bytes immediately following its one bitmap are real, nonzero data in every such app inspected, still not identified - a plausible guess is a function table (per the Title Sector format's own documented "function table" following icon data), but this is unconfirmed. Left untouched (copied verbatim from a real reference app) rather than guessed at. This doesn't apply to multi-frame icons, where that same space is simply the next animation frame(s) instead.

**The standard PS1 title-text field (Title Sector offset `0x04`-`0x4F`, meant to hold 2-byte Shift-JIS text) does not appear to be used by the PocketStation's own on-device browse screen at all.** A correctly SJIS-encoded custom title in that field (verified byte-correct by decoding a real app's own title the same way and getting a real, human-readable string back) never rendered on the browse screen in any configuration tested. Replacing *only* the 32×32 bitmap immediately after the standard icon (leaving the `0x04` title field untouched) was sufficient on its own to get a fully correct-looking custom result. Current working theory: the PocketStation's standalone LCD browse UI reads *only* the on-device-icon bitmap(s) (which real apps bake their own logo/text into as pixels), and the standard title field is for a PS1-console-side memory-card browser instead, which this project hasn't investigated.

### How to build a custom icon

1. Draw a 32×32 1-bit image per frame (any tool that can export a monochrome bitmap works, or generate it directly - see [`pk_timing_bench/`](../pk_timing_bench/)'s stopwatch icon for a worked example: procedurally drawing shapes into a 32×32 array, then packing 8 pixels/byte, bit 0 = leftmost).
2. Place the 128-byte-per-frame packed bitmap(s) either right after the standard icon's data (inline layout) or wherever a flags+pointer header points (indirect layout, following a real app's own values as a template).
3. If using the indirect layout, set the flags word's low 16 bits to the frame count, and the pointer word to `FLASH1_BASE` plus wherever you placed the bitmap data. The high 16 bits' exact effect on animation timing isn't confirmed - copy a real app's value for the animation speed you want until this is BIOS-traced.
4. For a single, static (1-frame) icon, leave the 128 bytes after the bitmap as copied from a real reference app rather than zeroing them, until that region's real purpose is confirmed.

## Memory access width (VRAM and FLASH1): word-only, confirmed the hard way

**Both LCD VRAM (`0x0D000100`) and FLASH1/app code+data (`0x02000000`) reject byte-granularity access on real hardware, even though this project's own emulator allows it without complaint.** Found via a real-hardware homebrew (this project's timing-benchmark app) that worked perfectly in the emulator and failed in two different, real, confirmed ways on an actual retail unit:

- **A blind `LDR`-value overwrite of `LCD_MODE`** (e.g. `mov r1,#0x40; str r1,[r0]`) instantly blanked the display and hung the device on first real-hardware boot. `LCD_MODE`'s true pre-app/POR value is undocumented, and this emulator's own default happens to already equal the value being written, so the bug was invisible in every emulator test. **Always read-modify-write `LCD_MODE`** - read the current value, OR/AND in only the bit(s) you actually want to change, write it back. Never assume you know its full starting value.
- **A byte-wide (`LDRB`/`STRB`) read-modify-write into VRAM** to set a single pixel produced an entire lit horizontal line (a whole 32-bit row) instead of one bit, on real hardware only. **Always access VRAM as full 32-bit words** - each row is already exactly one word (4 bytes), so a per-pixel set/clear is `ldr`/modify-bit/`str` on the containing row-word, never a byte-wide op.
- **A byte-wide (`LDRB`) read from FLASH1** (reading a font table one byte at a time) produced scrambled data on real hardware only. This one was actually already documented (see `hardware-notes.md`'s "Memory access timing": *"FLASH and BIOS ROM seem to be allowed to be read only in 16bit and 32bit units"*) but easy to violate by accident since the emulator doesn't enforce it. **Always read FLASH1 in 16/32-bit units** - word-align the address down, `ldr`/`ldrh`, then shift/mask in a register to extract a sub-word value if you need one.

None of these three failures reproduce in this project's own emulator as it stands - `core/src/lcd.c`'s `lcd_write8`/`lcd_mode_write8` and `core/src/memory.c`'s FLASH1 read path are all unconditionally byte-granular with no width restriction modeled. Don't trust emulator-only testing to catch this class of bug; if you're writing real homebrew, audit every VRAM/FLASH access for accidental byte-wide instructions before testing on real hardware.

## Timer0's COUNT register wraps at 0x10000, not 0x100000000

A fourth real-hardware-only issue turned up in the same timing-benchmark app, this time in application logic rather than a bus-width mismatch: a measurement loop read Timer0's `count` register once before a long operation and once after, then computed elapsed ticks via a plain 32-bit subtraction (`before - after`), assuming a full 32-bit free-running down-counter. On real hardware, a long-enough loop produced an `after` reading numerically *larger* than `before` - the classic sign of a counter wrapping past zero and reloading mid-measurement - and the naive 32-bit subtraction turned that into a huge, wrong-looking `0xFFFFxxxx` "negative" result instead of the small positive tick count that was actually true.

Diagnosis (via directly dumping raw before/after `count` snapshots rather than the computed delta, on real hardware): every raw reading came back with its upper 16 bits at zero, and subtracting the two raw values **modulo 65536** recovered the correct, expected result exactly - strong evidence Timer0's `count` is effectively a 16-bit register on real silicon (see `hardware-notes.md`'s "Timers" section). **If you time anything longer than a trivial number of instructions with a raw timer register, mask your computed delta to 16 bits** (`AND #0xFFFF` in Thumb-unfriendly ARM immediate form doesn't encode - use `LSL #16` then `LSR #16` instead; Thumb needs the same shift pair, since it has no immediate `AND` either). This is a safe no-op when no wrap occurred and the fix when one did.

### Open questions for future dev-kit work

- The flags word's high 16 bits (tentatively, per-frame animation delay) - only 3 real data points so far (values `1`, and `0x30`, roughly correlating with a static vs. a slow ~1-2s toggle), no BIOS/timer trace confirming the actual unit or formula.
- Whether the indirect-vs-inline icon layout choice is really governed by the Title Sector `0x50` header byte, or that's a coincidence of the small sample seen so far (2 indirect apps with `0x50=0`, 1 inline app with `0x50` matching its frame count) - needs more real apps, ideally with a BIOS trace of whatever code actually branches on this.
- What the data immediately following a *single-frame* indirect-layout icon's bitmap actually is (function-table entries? something else?) - real, nonzero data is present there in every such app checked, but its structure hasn't been reverse-engineered.
- The wider GUI/menu subsystem this session traced into while chasing the icon (a per-character glyph blitter at BIOS `0x0400383A`, indexed by `char_code - 0x30` into a font table; a generic scroll/animation blit reading a RAM scratch bu​ffer at `0x2D0` into VRAM; state structs at RAM `0x204`/`0x3D0`/`0x428`) is real and substantial, but only the one path relevant to the icon bitmap (the copy loop at BIOS `0x04002f8c`-`0x04002f9a`) has been fully traced. Understanding the rest (e.g. exactly how/when the menu decides to scroll, or whether the glyph blitter is ever used for anything app-controllable) is unexplored.
